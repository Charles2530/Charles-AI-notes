# 评测与证据链来源台账

这页专门记录数据划分、评测协议、污染检查、分桶报告和模型卡相关来源。它服务的写作原则是：评测不是排行榜，而是可复现、可归因、可回放的证据链。

## 使用方式

写评测类文章时，先把来源分成三类。

第一类是报告格式来源。Model Cards 和 Data Cards 帮助本站决定“评测结论应该披露什么”：模型用途、数据来源、使用边界、分群结果、失败模式、伦理风险和维护责任。这类来源不直接告诉读者哪个模型更强，而是提醒正文不要只写一个分数。

第二类是评测协议来源。HELM、OpenAI Evals 和 lm-evaluation-harness 帮助本站说明“评测如何可复现”：样本、prompt、scorer、few-shot 设置、采样参数、聚合方式和任务协议都要版本化。读者看到 benchmark 表格时，应先问协议是否固定，而不是立刻比较排名。

第三类是中文评测生态来源。SuperCLUE 和 FlagEval 适合作为中文读者进入 LLM 评测的入口，帮助理解中文任务、中文榜单和本土模型比较口径。使用它们时要保留边界：榜单结果不是模型能力全集，结论仍要回到样本构成、评分规则、任务覆盖和更新日期。

## 写作边界

评测来源不能被写成“某榜单说模型更强”。更稳的写法是：先说明评测要回答的问题，再说明数据、协议、指标和分桶，最后才讨论分数。若来源是平台或榜单，正文要标明它评测的是哪些任务、是否公开样本、是否允许提交调参、是否使用自动 judge、是否报告置信区间或失败样本。

对于模型发布页、系统卡和论文表格，本站优先引用原论文、官方报告或官方项目页；中文榜单和媒体解读主要学习任务组织方式、指标表达和中文读者入口。若同一模型在不同榜单上结论冲突，应把冲突当作评测协议差异来解释，而不是简单判断谁对谁错。

## 文章模板

改写评测相关页面时，可以按这条顺序组织正文。

先定义评测对象：模型版本、系统组件、prompt、检索、工具、采样参数、judge 和后处理是否固定。接着定义数据：train、dev、test、holdout 的用途，是否有近重复污染，数据版本和 metadata 是否能支撑分桶。然后定义指标：指标到底奖励什么，是否符合任务风险，是否需要 pass@k、F1、calibration、人工评分或执行验证。

正文中间要讲统计不确定性。样本数少时，1-2 分变化可能只是噪声；两个模型比较时，优先看同一批样本上的 paired difference，而不是孤立平均分。若使用 LLM judge，要说明 judge prompt、位置偏差、长度偏差、复评策略和人工抽查。

最后讲行动。评测报告应该能回答：是否发布、是否阻断、退化在哪个桶、失败能否回放、下一步是补数据、改目标、改 prompt、改系统还是更新评测集。不能驱动行动的分数，只是装饰性数字。

这套模板适用于基础页、训练页、推理页、量化页、VLA 页和论文精读页。不同页面的指标会变，但证据链不变：对象要固定，数据要干净，指标要匹配，分桶要揭示风险，失败要能复现。

## 优先级

如果篇幅有限，评测文章优先写三件事。第一，评测协议是否固定，因为协议漂移会让分数不可比。第二，关键分桶是否退化，因为平均分最容易掩盖高风险失败。第三，失败样本能否回放，因为不能复现的错误很难进入下一轮数据和系统修复。其它内容可以后补，但这三项缺失时，评测结论通常不够可信。

中文评测材料的使用方式也按这个优先级来：先看它有没有清楚说明任务、样本和评分协议，再看它是否展示分项能力和失败类型，最后才看排行榜名次。若只给总分，不给样本、协议和分桶，本站只把它当作阅读入口，不把它当作强证据。

后续新增评测来源时，也应优先补“它能帮助本站讲清哪一个评测环节”，而不是只补链接。
