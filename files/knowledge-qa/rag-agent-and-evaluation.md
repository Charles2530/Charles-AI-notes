# RAG、工具调用与答案评估问答

一个答案带有引用、格式也正确，仍可能使用了过期规则或把例外条件漏掉。排查时需要保存模型实际看到的证据和工具实际返回的结果。

## 有引用为什么还会答错

引用可能只与主题相关，没有支持具体结论。例如当前政策为7天，旧政策为14天，用户签收9天，引用真实的旧页面仍会导致错误判定。链接存在与证据适用是两项检查。

把答案拆成版本、范围、事实和推导，逐项核对来源。若证据根本没进入上下文，先修检索；若正确证据已完整进入，再看条件理解与计算。见[Prompt与RAG](../foundations/prompt-engineering-cot-and-rag-basics.md)。

## 检索recall很好，最终答案为什么仍差

Recall只说明相关片段是否在候选集。Rerank可能把它排到后面，上下文截断可能删掉例外，生成器也可能忽略冲突版本。候选中出现正确文档并不保证最终prompt里包含足够证据。

保存召回候选、排序后片段、实际prompt与引用映射，逐层检查同一题。若问题是“例外条件分在另一chunk”，提高top-k可能缓解，但合理保留条款结构更直接。见[RAG系统](../inference/rag-agents-and-long-context-systems.md)。

## 长上下文能不能直接替代检索

长上下文允许同时放更多资料，检索决定从更大资料池中选哪些内容。资料短、稳定、每题都要综合时，直接放入可能简单；资料频繁更新、有权限或版本限制、体量远超窗口时，仍需要检索或过滤。

两者还可组合。更多上下文带来token成本、prefill时间和证据竞争，不能假设“放得下就一定用得好”。应在相同问题上比较证据覆盖、答案质量和延迟，而非只比较最大窗口。

## Agent说“调用成功”，怎样确认

自然语言说明不是执行记录。程序应保存工具名、已校验参数、调用标识、实际返回状态与结果，再把结果提供给模型。超时、权限失败和空结果需要明确状态，不能把失败默认成成功。

重试还涉及幂等性。重复读取通常容易处理，重复支付或写入则可能产生重复副作用，需要工具自身的请求标识和状态校验。Agent循环要受预算和停止条件控制，避免同样失败反复调用。见[Agent运行时](../inference/rag-agents-and-long-context-systems.md)。

## JSON合法为什么不等于调用安全

JSON schema可以约束字段类型与部分取值，无法单独判断订单是否属于当前用户，或目标资源是否允许修改。权限、范围、业务条件和执行前状态应由程序校验。

从检索文档读到的指令不应获得系统权限。角色分隔有帮助，但不是完整的prompt injection防御。验证应针对工具能够实际产生的动作，而非仅检查模型有没有写出漂亮解释。

## LLM-as-judge分数可以直接当真值吗

Judge是一个测量过程，也可能受答案长度、顺序、文风与自身知识影响。交换候选顺序、对争议样本人工复核、用确定性规则验证可验证部分，有助于判断它在测什么。

如果用同一个judge训练又只用它评估，策略可能学会满足它的偏好。应保留独立评价或具体任务结果，报告judge配置与评分依据。对于数值、代码和引用，能直接核验的部分不要全部交给风格判断。见[评测基础](../foundations/data-splits-metrics-and-evaluation-basics.md)。

## 没找到证据，应该拒答还是继续推理

取决于问题是否需要外部事实，以及已知信息是否足够。订单规则缺失时不能凭常识补政策；纯数学问题可能只需要给定条件。可以给出明确的条件答案，说明缺哪个决定性字段。

无答案测试应与可回答测试同时存在，否则系统可能通过一律拒答获得表面安全，也可能为追求回答率编造内容。评价需要同时衡量正确回答、错误回答和适当拒答，不能只看覆盖率。
