# 外部教程的来源、改编与证据边界

本站会参考教材、官方文档、技术博客、论文和源码，但“参考”不等于可以把原文搬进来。每一页需要同时满足三个条件：读者能沿着清晰的教学顺序学会一个对象，关键事实能回到可靠来源，页面中的文字、代码、图像和公式使用方式没有越过来源许可。

## 先区分五种材料

| 材料 | 适合怎样使用 | 需要单独核对什么 |
| --- | --- | --- |
| 自己推导的公式与小例子 | 独立讲解和练习 | 公式假设、符号一致性、数值是否算对 |
| 官方文档与 API | 解释当前接口、参数和限制 | 版本、适用硬件、文档许可 |
| 论文 | 说明方法、实验设置和原作者结论 | 原图、表格、代码和数据集许可分别处理 |
| 技术博客或课程 | 借用叙事顺序、问题拆分和直觉 | 作者许可、是否过时、是否把特定设置说成普遍规律 |
| 源码与示例代码 | 进行版本化对照或写独立实现 | 仓库许可证、依赖许可证、commit、是否含第三方代码 |

模型卡、博客文章、论文 PDF、项目仓库通常不是同一个许可对象。一个仓库有 MIT 许可，也不意味着其中引用的论文图和第三方图片可以一起复制。

## 先把页面的真实状态说清楚

“有参考链接”不能自动推出“全文独立原创”。页面至少要在编辑记录中标出下面三种状态之一：

| 状态 | 含义 | 发布时怎么写 |
| --- | --- | --- |
| 独立讲解 | 只保留事实、公式和接口，例子、顺序与正文由本站重新组织 | 可以写“本站独立讲解”，仍需列出事实来源 |
| 许可范围内改编 | 原作者或仓库明确允许翻译、改编或再发布 | 写清原作者、原文、许可证、改动范围和署名 |
| 待逐句核查 | 页面来自旧稿、多人协作或模型辅助改写，尚未完成相似表达与素材审计 | 先缩小为阅读导引，或标成待审，不宣称全文原创 |

本站当前不能因为某一页列出了论文、博客和源码链接，就把它归入第一类。尤其是历史页面和批量生成的论文笔记，需要重新检查独特比喻、段落顺序、表格、图注和代码片段。来源记录解决的是事实追溯，不能代替文字相似度和许可证核对。

## 三种改编模式

### 独立讲解

只使用事实、概念和公开公式，重新选择例子、结构和文字。适用于许可不明确的博客、作者项目页和快速变化的工程文章。页面仍应给出原始链接，并明确哪些内容是本站的推导或实验协议。

## 历史批量融合页面要单独看待

仓库里的 `enrich_log.md` 记录过一轮对 Datawhale `llm-algo-leetcode` 教程的批量融合，日志统计为 101 个页面吸收了算法基础或复杂度分析。日志同时记录代码和外部图片没有直接复制，但这只能说明当时的素材处理方式，不能证明每页文字都已经脱离原文结构，也不能替代许可证和逐句相似性检查。

因此，凡是出现在这份历史融合清单中的页面，都暂时采用“待逐句核查”状态。后续编辑应把独特标题、例子顺序、比喻、表格和代码接口重新组织，并为当前仍有效的事实补上官方文档、论文或版本化源码。原链接失效时保留历史记录，同时寻找项目仓库或新的官方入口；找不到可靠替代物，就把它降级为阅读导引，不继续扩写成本站事实。

`source_overlap_report.py` 默认只扫描 `.firecrawl/blog-source-research-1109/` 中的 60 份缓存文本。2026-11-10 另用 GitHub API 临时抓取了 Datawhale 当前 `main` 分支 `docs/` 下 391 份可读 Markdown 做抽样全量审计，结果同样未发现长句级精确重合。两次结果都只覆盖抓到的当前文本，不能排除标题、例子顺序、段落结构、旧版本或未抓到的资源存在相似，也不能推出全站已经完成版权审计。

`source_similarity_report.py` 进一步用 CJK 字符片段和英文词片段做近似重合分诊。本轮对 329 个页面和 73 份本地文本缓存没有筛出达到默认阈值的候选；原有精确脚本在其中 60 份来源文本上建立索引。它只能捕捉同语言的轻微改写，不能可靠识别跨语言翻译，也不判断许可证或抄袭；出现候选时仍需人工逐段对照原文和编辑记录。

### 许可范围内的译介或改编

只有在页面或仓库明确允许相应行为时，才保留原结构或进行较近的翻译。顶部写出原作者、原始标题、链接、许可证、改动说明和非商业/相同方式共享等条件。CC BY-SA、Apache、MIT 等许可的义务并不相同，不能只写“来源于某博客”。

### 导读与外链

如果许可含 ND、需要作者事前联系，或页面包含不明来源的图片和代码，就只在本站写问题地图、术语解释、阅读顺序与实验入口，让读者回到原文阅读。不要发布近似逐段翻译，也不要把“我没有收费”当成自动许可。

## 一页正文的来源字段

在草稿开始前建立以下记录，放入 PaperPilot 或页面的来源说明中：

```yaml
source_ref: "paperpilot://..."
author_or_org: "..."
original_title: "..."
url: "https://..."
accessed_or_version: "2026-11-10 / commit ..."
adaptation: "independent explanation|permitted adaptation|reading guide"
license: "verified URL or unknown"
third_party_assets: "checked|pending|not used"
local_claims: ["hand calculation", "local benchmark", "not yet measured"]
```

`license: unknown` 不等于不能引用；它意味着只能采取更保守的独立讲解和链接方式。`local_claims` 用来阻止论文 benchmark、本站小程序和真实实验在写作时被混成同一种证据。

## 图、代码和公式分别处理

论文原图和第三方图片不要因为正文已经引用论文就自动复制。优先使用自己绘制的结构图、Mermaid 或手算表，并在图注中说明“本站重绘/示意”。代码可以按仓库许可证保留必要片段，但应记录 commit、版权声明和修改部分；更适合教学的做法是写一个独立的最小实现，再链接原始代码。

公式本身通常属于事实或数学表达，但符号选择、独特叙事和整段解释仍可能构成原文表达。本站应重新组织推导，给出自己的数值例子，并核对边界条件。

## 发布前的五项检查

1. 每个外部事实都有原始链接、版本或访问日期。
2. 论文结论、官方 benchmark、本站小程序和本地真实实验被分栏记录。
3. 图片、代码、表格和正文的许可分别核对。
4. 含 ND 或需联系作者的材料没有进入近似翻译队列。
5. 页面保留一个可运行的自测、反例或实验合同，而不是只堆外链。

## 一篇新教程的实际查阅顺序

先找一个读者能复算的失败现象，再找一份官方实现或原论文确认对象和边界。接着从两到三份成熟教程中比较它们怎样铺垫术语，选出适合本站读者的一条路径。正文写完后，单独做一次代码、公式、图像和许可证核对。

这样做会留下四类记录。原始事实回到论文或官方文档，结构灵感记录文章链接，本站解释和算例单独标注，真实运行结果进入 `server_monitor` 或 PaperPilot。四类材料混在一个“参考资料”段落里，后续维护时很容易把别人的 benchmark 误写成自己的结果。

这一套规则服务于持续维护。网站教程可以借鉴成熟来源的结构和解释优势，但最终应成为自己的课程组织、自己的例子和自己的证据链。

## 让技术说明像人在讲，而不是像模板在排版

同一套标题和段落顺序套在三百篇文章上，读者很快会感觉到机器的节奏。写新页时，先找一个真实的入口：一条报错、一组 shape、一次失败的对照、论文里一个容易读错的数字，或者一个需要作取舍的工程决定。开头先把这件事说清楚，再引入术语。没有具体入口时，就缩小题目，不用抽象的“本文将全面介绍”来填空。

一个段落只推进一个判断。公式后面说明它改变了哪一个数，图后面说明读者应该看哪条线，实验数字后面说明它支持什么以及还不能支持什么。把“首先、其次、最后”“进一步来看”“这意味着”留给确实需要顺序或因果的地方。每页不必拥有相同数量的小标题、表格和总结段。

技术事实、本站手算、本站 smoke test 和真实运行结果要用不同的说法。可以写“论文报告”“下面这个例子算出”“本地脚本只检查数据流”“目标 GPU 尚未测量”，不要用一个笼统的“实验表明”把它们混在一起。涉及个人工作流时，只写 PaperPilot 或 `server_monitor` 里确实存在的记录，不凭空补充运行时间、成功率和硬件结果。

改写完成后，做一次只看文字的复核。删掉没有增加事实的过渡句，合并重复的结论，检查每个“通常、显著、有效、稳定”后面是否紧跟条件或数字。若一段读起来很顺，却找不到具体对象、动作和证据，优先把它改短或换成一个可复算的例子。
